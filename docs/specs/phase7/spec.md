## Goal

Tie every training sample and every reported number to the exact thing that
produced it, then run the seven experiment arms as measured experiments. The
report is generated by script; a number without a run record does not appear.

## What already exists (and must not be broken)

| Piece | Where | Phase 7 uses it as |
|---|---|---|
| JSONL trajectory protocol | `agent_env/trajectory_logger.py:1-10` | the versioned record format |
| step/episode records | `MultiTurnDeliveryEnv`, `EpisodeRecord.to_jsonl_records` | producer of samples |
| dataset builders | `training/data/build_sft.py`, `build_dpo.py` | consumers; semantics must not change |
| matched-state clone | `build_dpo.py:61-70` (`copy.deepcopy`) | the only licensed counterfactual basis |
| report generator | `training/report.py` | `docs/results.md` is generated, never hand-edited |
| pre-registered targets | `docs/results.md` | acceptance columns; 1/7 arms measured |

## 1. Provenance (additive, versioned)

Every trajectory step gains optional fields; nothing is renamed or removed:

```
{"record": "step", "schema_version": 2, ... existing keys ...,
 "provenance": {
   "model_id": "rule_baseline" | "sft" | ... ,
   "prompt_hash": "<sha256:16>",        # system prompt actually used
   "schema_hash": "<sha256:16>",        # action catalogue JSON
   "benchmark": {"name": "fault_injection_v1", "sha256": "<32 hex>"},
   "command_id": "<cmd-...>"            # when the step came through the runtime
 },
 "receipt": {"execution_status": "completed", "failure_code": null}}
```

Rules:

- an absent `schema_version` means v1; v2 records carry it explicitly;
- dataset builders ignore unknown fields, so old inputs produce byte-identical
  datasets (tested);
- a sample with `prompt_hash`/`schema_hash` that disagrees with the run record
  is not trainable — the loader refuses it rather than silently training on
  drifted data;
- the episode record carries the same provenance block once.

## 2. Run records

Every evaluation or training run writes `runs/<kind>/<name>.json` containing:
condition/arm, model id, prompt hash, schema hash, benchmark name + sha256,
seeds, budgets (Phase 5/6 fields), and the artifact paths it produced.

`training/report.py` renders a cell only when its run record exists and matches
the report's inputs; otherwise the cell reads `unverified`, never a number.

## 3. Results are generated

`docs/results.md` is produced between explicit markers:

```
<!-- BEGIN GENERATED: arms -->
...
<!-- END GENERATED: arms -->
```

Prose outside the markers may be edited by hand; anything inside is overwritten
by `python -m training.report`. The generator refuses to run if its inputs are
missing rather than emitting a partial table.

## 4. The experiment matrix

Seven arms, targets already pre-registered in `docs/results.md`:

| arm | policy source |
|---|---|
| `rule_baseline` | rules (measured: 76.1% recovery, 1/7 done) |
| `sft` | SFT checkpoint |
| `sft_dpo` | SFT then DPO |
| `ppo_terminal` | PPO with terminal reward |
| `ppo_progress` | PPO with progress reward |
| `opd_pure` | on-policy distillation |
| `opd_warmup_ppo` | OPD warm-up then PPO |

All arms run on L1 with the same `Budgets` (turns, characters, wall) and the
same frozen 400-episode benchmark. A run with different budgets is not entered
into the table (Phase 6 ablation rule).

## 5. Reward-hacking and credit-assignment audit

The report adds an audit block per arm:

| Signal | Definition | Why |
|---|---|---|
| `proxy_gap` | mean progress reward − task success | rewards rising while success is flat |
| `repeat_rate` | identical call within 3 turns | exploiting the step loop |
| `false_success_rate` | claim without environment confirmation | exploiting the evaluator |
| `flat_vs_span_credit` | delta between flat and span credit assignment on the same rollouts | whether credit assignment is doing anything |

An arm whose proxy gap grows while success does not is flagged in the report,
not silently accepted.

## 6. Distribution shift, stated honestly

- Every result is labelled **L1 only**; no row may imply physical-robot success.
- L2 status is attached from `benchmarks/calibration_v1.json` when present; a
  family marked `calibrated: false` is called out in the report header.
- Sim-to-real claims require L2 and, later, L3 data; the report has no column
  for them and the generator rejects such fields.

## 7. Counterfactual recovery, gated

Counterfactual analysis ("what if the policy had chosen the other action") is
allowed only when the state can be restored exactly and that restoration is
verified:

- L1 only, through `clone_env`; the clone must produce an identical state hash
  (observation, phase, step index, outcome) before being used;
- L2/L3 are forbidden — the runtime has no verified matched restore;
- a counterfactual sample without a matching state hash is dropped and counted
  in the run record.

## Non-goals

- No GPU training in this phase; arms are run as separate, recorded experiments.
- No change to the frozen benchmark, rewards, or action vocabulary.
- No L2/L3 counterfactuals or sim-to-real claims.

## Open questions for approval

1. **Versioning.** Recommendation: additive fields + `schema_version: 2`;
   absent means v1.
2. **Hashes.** Recommendation: sha256 truncated to 16 hex for prompt/schema,
   full hash for manifests, computed from file bytes.
3. **Run-record location.** Recommendation: `runs/<kind>/<name>.json` next to
   the evaluation output it describes.
4. **Counterfactual scope.** Recommendation: L1 + verified clone hash only;
   the runtime-side ledger is not a state store and cannot restore state.
